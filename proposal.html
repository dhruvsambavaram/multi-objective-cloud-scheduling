Problem and Motivation

A cloud platform receives batches of tasks, each with a CPU demand, a memory demand, a duration, a release time and a deadline. It runs them on a small pool of heterogeneous virtual machines that differ in capacity and price. We have to decide which task runs on which machine and when. Finishing early, spending little, and meeting deadlines pull in different directions: packing work onto fewer, cheaper machines saves money but delays completion. We study this trade-off quantitatively, and we ask when an exact optimiser is actually worth it compared with the simple rules used in practice.

Scope. Offline, deterministic batch scheduling: 10–100 tasks, 3–10 machines, integer time slots (1 slot = 1 min), no preemption. Online arrivals and rescheduling are out of scope.

Formulation

Binary ximt = 1 if task i starts on machine m at slot t; ym = 1 if machine m is used; completion Ci, tardiness Ti, makespan Cmax, machine lease end Em.

min  α · Cmax / LB  +  β · Σm (Fm ym + km Em) / Costgreedy  +  γ · Σi wi Ti / Σi pi

Subject to: each task starts exactly once, at or after its release time; at every slot the running CPU and memory on each machine stay within its capacity; Ci = Σ (t + pi) ximt; Ti ≥ Ci − di, Ti ≥ 0 (soft deadlines); Cmax ≥ Ci; Em is at least the end of every task on m. Each objective term is normalised to a dimensionless quantity — makespan relative to a provable lower bound, cost relative to a greedy schedule, and the fraction of work-time that is late — so the weights are genuine relative importances.

Method and Solvers

Our primary optimiser is Google OR-Tools CP-SAT, using optional interval variables and cumulative constraints, with a time limit and the reported optimality gap. Its model size does not depend on the horizon. For comparison, we solve the time-indexed MILP above with Pyomo + HiGHS on small instances, where its size grows linearly with the horizon. Baselines: First Come First Served, Shortest Job First, greedy least-loaded, and a cost-aware greedy. An independent checker validates every schedule.

Data

We use seeded synthetic workloads with an offered-load knob ρ and a deadline-tightness knob τ. We then validate the results on samples of the public Google 2011 cluster trace (CPU and memory requests and observed runtimes from one task_events part). We document every assumption made in the conversion.

Questions for the Analysis

Does optimisation always beat greedy, and does the answer change with load? When do deadlines become infeasible? Does a tightly optimised plan stay good when durations are wrong?
